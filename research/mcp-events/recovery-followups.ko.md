# 수신됐지만 실행 승인 요청으로 이어지지 않은 복구 이벤트

[English](recovery-followups.md)

[#79](https://github.com/abruption/dots-tailscale/issues/79)는 이벤트 수신 확인 뒤에도 Dots가 claim을 받지 않은 채 남는 문제를 다룹니다. HTTP 200은 콜백 수신 확인이며, 작업 검토·터미널 접근·시작 명령 실행까지 확인한 결과는 아닙니다. 이 선택적 broker 기능은 **같은 장애**를 다시 확인해 달라는 요청을 제한된 횟수로 보냅니다. 실행 권한을 주거나 Dots의 응답을 보장하지는 않습니다.

## 정책과 한도

기본값은 꺼짐입니다. 검토한 서버는 다음 선택적 설정을 받습니다.

```json
{
  "recovery_unclaimed_reminder_interval_seconds": 600,
  "recovery_unclaimed_reminder_maximum": 3,
  "recovery_unclaimed_reminder_lifetime_seconds": 7200
}
```

간격은 300~3600초의 정수, 최대 횟수는 1~3의 정수, 유효기간은 간격보다 길면서 300~86400초의 정수여야 합니다. 참·거짓 값이나 문자열은 거부합니다. 끌 때는 간격을 `null`로 설정하고 `false`나 0을 쓰지 마세요. 예제 설정은 복구와 이 기능 모두 꺼진 상태를 유지합니다.

간격은 선택된 요청의 실제 2xx 콜백 응답 기록부터 계산합니다. 활성 구독이 여러 개라면 대기·재시도·전송 중인 작업이 끝난 뒤, 가장 최근에 추적한 성공 응답을 기준으로 대기 시간을 잡습니다. 스케줄러가 처음 채택한 실제 수신 기록으로 해당 장애의 만료 시각을 고정합니다. 이후 재알림, 정책 제한 해제 이벤트, 재시작, 구독 갱신, 기능 재활성화로 횟수를 초기화하거나 기록된 기한을 늘리지 않습니다.

장애당 의미상 다른 **재알림 이벤트를 최대 3개** 만듭니다. 네트워크 전송 재시도는 기존 outbox 한도를 별도로 따릅니다. 재알림은 각각 `incident:unclaimed:generation` 형식의 요청 식별자를 쓰며, 기존 복구 이벤트 payload 규격을 유지합니다. 원래 이벤트·장애·수신/전송 중/종료된 전달 기록과 claim 이력을 보존합니다. 수신된 행을 초기화하거나 같은 장애를 새 장애로 만들지 않습니다.

## 재알림 조건

최신 외부 장애 관측, 아직 대기 중인 정확한 장애, 현재 claim 자격, 유효한 활성 구독이 모두 필요합니다. 사전 점검 중단 보고가 있으면 재알림을 멈춥니다. 이미 claim을 받았거나 실행 결과가 불명확한 작업에 시작 요청을 다시 보내지 않습니다. 일일·간격 한도, 로컬 예산, 플랫폼 거부와 명시적 중지 의사는 계속 적용됩니다.

일정 결정과 의미상 중복 방지는 기존 SQLite 쓰기 트랜잭션 안에서 처리합니다. 전송 직전에도 현재 장애·정책·수신 기한·구독을 다시 확인합니다. 관측이 오래됐거나 정책이 일시적으로 막으면 전송을 보류합니다. claim 발급, 외부 복구, 사전 점검 중단, 만료, 기능 비활성화, 더 새로운 정책 이벤트가 있으면 대기·재시도 중인 의미상 재알림을 취소합니다. 정상 관측을 수신하면 장애를 닫는 것과 같은 쓰기 트랜잭션에서 이 대기열을 취소하므로, 백그라운드 선택기가 다시 찾아야 하는 상황을 남기지 않습니다. 이미 전송 중이거나 수신·종료된 행을 바꿔 억지로 재전송하지 않습니다.

전송을 허용한 뒤 이미 네트워크로 나간 콜백은 claim이나 중지 요청과 시점이 겹쳐도 회수할 수 없습니다. 늦게 도착하거나 중복된 이벤트도 데이터이며, 명령 실행에는 새로 승인된 claim이 필요합니다. 장애당 claim 한 번과 결과 불명 상태의 재실행 방지 조건은 유지합니다.

의미상 대기열이 중지돼 선택한 이벤트가 취소 대상이면, 늦게 연결된 새 구독에는 기존 원래 이벤트·현재 정책 이벤트의 전달 경로를 유지합니다. 일시 보류일 때는 이 경로로 되돌아가지 않습니다. 사전 점검 중단을 풀거나 새 의미상 이벤트·실행 권한을 만들지 않으면서 기존 기본 이벤트의 동작을 보존합니다.

기존 정책 제한 해제 이벤트를 먼저 처리합니다. 재알림은 그 이벤트의 실제 수신을 기다리며 기존 횟수와 만료 시각을 유지합니다. 두 종류의 재알림을 한꺼번에 만들지 않습니다. 정해진 시각에 즉시 전달·실행된다는 약속은 아닙니다.

## 수신 근거, 과거 기록과 중지

`recovery_delivery_receipts`는 기능이 켜져 있을 때만 새 콜백의 성공 응답을 전달 결과와 같은 트랜잭션에 기록합니다. 기본 꺼짐 상태에서는 수신 기록이 계속 쌓이지 않습니다. 꺼져 있을 때 받은 응답은 이후 기능을 켜도 추적된 수신 시각을 얻지 않습니다. 과거 `received` 행, 장애 생성 시각, 관측 시각이나 상태 조회로 수신 시각을 추정하지 않습니다. 이런 근거가 없는 과거 수신 행은 `legacy_receipt_unavailable`로 표시하며, 기능을 켠다고 재전송하지 않습니다. 운영자 검토나 별도로 승인된 복구가 필요합니다.

`recovery_followups`에는 추적한 장애마다 제한된 기록 하나를 보존합니다. 스케줄러가 만료나 횟수 소진을 저장했다면 시계 역행, 설정 변경, 재시작 뒤에도 해당 장애의 종료 조건을 유지합니다. 읽기 전용 조회 결과만으로 이 종료 조건을 영속 저장하지는 않습니다. 그 밖의 시계 역행도 횟수를 되돌리지 않고 전송을 보류합니다. 최대 횟수를 이미 대기 중인 세대보다 낮추면 횟수를 돌려주지 않고 해당 전송을 막습니다. 기능을 끄면 대기 중인 의미상 재알림을 취소하고, 기존의 늦게 연결된 구독에는 원래 이벤트나 현재 정책 이벤트를 선택하는 동작을 복원합니다. 다시 켜도 취소된 전달이나 원장을 초기화하지 않습니다. 다만 재활성화 뒤 새로 검증된 구독은 현재 조건이 허용하면 기존 의미상 세대를 받을 수 있습니다. 이는 새 구독과 outbox의 쌍을 만드는 것이며, 새 재알림 세대를 만들거나 이전 전송 행을 초기화하는 동작은 아닙니다. 구독을 해제하면 해당 구독으로 보내지 않고, 갱신했다고 만료된 전달 행을 다시 대기로 바꾸지도 않습니다.

추가 저장소는 재알림 기록 1,000개, 수신 기록 10,000개로 제한합니다. 한도에 도달하면 추가 근거 기록·일정 생성을 보수적으로 중단하고 운영자 확인을 표시합니다. 용량이 차면 수동 검토가 필요할 수 있으며, 자동 유지보수 절차나 무제한 운영 기간을 제공하지 않습니다. 자동 삭제하거나 새로운 실행 예산으로 취급하지 않습니다. 중지를 풀려고 기록을 지우거나 과거 DB를 복원하지 마세요. 이 한도가 기존 이벤트·실행 승인 이력 전체의 크기까지 제한하는 것은 아닙니다.

## 읽기 전용 상태와 운영자 알림

`get_current_recovery` 응답에 `unclaimed_followup`을 추가하며, 조회만으로 이벤트를 만들지는 않습니다. 다음을 보여줍니다.

- 선택된 정책, 생성한 재알림 수와 기록된 만료 시각
- 현재 활성 구독에 대한 선택된 전달 근거, 실제 수신 시각과 응답 상태
- 다음 재알림이 허용될 때의 참고 시각 `next_reminder_at`. 마지막 가능한 재알림 뒤에는 `awaiting_response`와 별도 `response_deadline_at`을 표시하고 다음 재알림 시각은 제시하지 않습니다.
- `waiting`, `due`, `claimed`, `preflight_reported`, `observation_stale`, `legacy_receipt_unavailable`, `expired`, `exhausted` 같은 고정 사유
- 횟수 소진·만료·근거 부족 시의 `operator_attention`

콜백 주소, 서명 비밀과 구독 ID는 출력하지 않습니다. 예정 시각이 claim이나 미래의 실행 허가가 되지는 않습니다. 조회는 근거를 만들어내거나 시계 기준을 갱신하거나 재알림 예산을 쓰거나 알림을 보내지 않습니다.

기능이 켜진 대기 장애에 사전 점검 중단 보고가 없다면, 실제 수신을 근거로 만든 기록의 만료 시각에 `expired`와 `operator_attention`을 표시합니다. 마지막 콜백이 아직 `sending`이어도 같습니다. 스케줄러가 이 종료 상태와 경고를 한 번 저장합니다. 최초 실제 수신이 늦었다면 그때 고정한 유효기간을 따르므로, 장애 자체가 오래됐다는 이유로 방금 보낸 재알림을 기한 초과로 판단하지 않습니다.

아직 수신을 근거로 만든 기록이 없다면, 최신 관측·실행 자격·활성 구독 조건을 갖춘 장애의 전달이 불명확한 채로 장애 생성부터 설정된 유효기간을 넘었을 때 `delivery_unconfirmed`를 표시합니다. 이 시간은 근거 없는 상태를 얼마나 오래 조용히 둘지 정하는 기준입니다. 수신 시각·재알림 시작 근거·새 이벤트·전송 재시도·실행 권한을 만들어내지는 않습니다. 저장된 장애 시각과 outbox로 재시작 뒤에도 상태를 계산할 수 있습니다.

전송이 종료된 실패로 확정됐다면 다른 조건이 맞을 때 `delivery_unconfirmed`를 즉시 표시합니다. 장애 나이에 따른 대기는 아직 불명확한 전달에만 적용하며, 확정된 종료 실패에는 적용하지 않습니다.

스케줄러는 만료·소진을 확인하면 이를 저장하고 고정된 비민감 로그 경고를 한 번 남깁니다. 별도로 설정한 운영 감시기가 구조화된 `operator_attention`을 사용할 수 있습니다. **이 변경만으로 텔레그램·이메일 알림 경로를 설치하지는 않습니다.** 운영자 경고의 끝단 연동은 #80에서 추적합니다. Dots 작업의 구독이 있다는 사실만으로 운영자가 소진 경고를 봤다고 판단하지 않습니다.

## 반영·원복과 검증 범위

`recovery_followups.py`, `recovery_core.py`, `event_core.py`와 통합 서버의 생성자 인자 연결을 하나의 검토된 소스 구성으로 반영해야 합니다. 비공개 통합 어댑터가 새 설정을 명시적으로 전달해야 하며, 공개 연구용 서버로 덮어쓰지 마세요. 운영에 남아 있는 구버전 예산·간격 도구는 확장된 생성자를 거부할 수 있습니다. 이 저장소에서 갱신한 도구는 이후 정책만 바꿀 때 새 인자의 정확한 연결 형식을 받지만, 여전히 `event_core.py`나 `recovery_followups.py`를 복사하지 않으므로 기능 설치기로 쓸 수 없습니다. 독립 터미널, 코드·설정 백업과 실행 승인 원장 보존을 갖춘 별도 해시 고정 배포를 준비하세요. 이 PR은 그 배포를 수행하거나 운영 정책을 켜지 않습니다.

코드 원복 전에는 재알림을 끄고 콜백 작업을 안정적으로 중단하세요. 이전 코어의 일반 대기 전달 경로는 새 의미상 재알림 ID를 선택하지 않지만, 새 진단·중지 기록도 이해하지 못합니다. 이전 코드로 그 ID를 직접 전송하거나 예전 DB를 복원하지 마세요. 이미 전송 중인 콜백은 회수할 수 없으므로 기존 장애·claim 규칙은 계속 필요합니다.

격리 시험은 가상 시계·SQLite·가짜 구독·서명된 콜백 fixture를 사용합니다. 수신 후 미실행, 정책 전환, 재시작·동시 일정 결정, claim·중지 뒤 지연 전달, 오래된 관측, 구독 갱신·만료, 만료·소진 보존, 과거 수신 기록과 용량 제한을 다룹니다. 인증된 관측 수신부터 백그라운드 전달까지 실제 구현 경로를 사용하는 시험도 포함합니다. 실제 플랫폼 실행, VM 교체나 자연 장애의 무인 복구 시험은 아닙니다.
