# 운영 복구 한도 24회 변경안

[English](recovery-budget.md)

[#80](https://github.com/abruption/dots-tailscale/issues/80)의 운영 정책 변경안입니다. 명시적으로 설정한 **12회** 한도를 **최근 86,400초 동안 claim 최대 24회**로 높입니다. 이 문서가 병합되거나 dots-tailscale을 설치하는 것만으로 운영 서버의 설정이 바뀌지는 않습니다.

패키지 기본값은 계속 **최근 24시간 최대 3회**입니다. 이번 운영 변경안은 전역 실행 간격 **3,600초**, 복구가 확인된 뒤 새 장애에 적용하는 간격 **600초**를 유지합니다. 성공·실패·결과 불명·미보고 여부와 관계없이 발급된 claim은 계속 집계합니다. 집계 기간을 초기화하거나 횟수를 돌려주지 않으며, 로컬 복구 조정 기능이나 watchdog의 별도 한도도 바꾸지 않습니다.

## 변경 준비

기존 비공개 서버 설정에서 다음 키 하나를 바꾸는 안을 검토합니다.

```json
{"recovery_max_claims_per_24h": 24}
```

`recovery_cooldown_seconds=3600`, `recovery_new_incident_cooldown_seconds=600`, 인증·메일 연동·구독 설정 등 다른 값은 유지합니다. 예제 파일로 비공개 설정 전체를 덮어쓰지 마세요. 일반 `config.example.json`은 복구가 꺼진 상태를 유지하며 이번 운영 한도를 기본값으로 넣지 않습니다.

검토된 `new_incident_policy_deployment.py`에 선택적인 `--max-claims-per-24h` 옵션을 지원합니다. 생략하면 기존 한도나 암묵적 기본값을 보존하고, 지정할 때는 1~24의 정수만 받습니다. 기존 설정이 잘못됐다면 새 값으로 조용히 고치는 대신 거부합니다.

도구의 보호된 준비 경로, 소스 해시 고정, 배포 잠금, 최신 정상 관측과 진행 중인 작업이 없어야 한다는 조건은 유지합니다. **열린 장애나 전송 중인 이벤트가 있으면 적용을 거부합니다.** 독립 복구 터미널을 준비하고 이 조건을 충족하는 점검 시점을 확보하세요. 진행 중인 장애의 실행 제한을 우회하는 도구가 아닙니다.

이번 한도 변경에서는 이미 설치된 코어를 독립적으로 검증해 그대로 준비하고, 두 코어 인자에 같은 해시를 사용합니다. 기존 통합 서버도 확인해 해시를 고정하세요. 연동 코드를 바꿀 필요가 없도록 이미 지원되는 정책 인자를 전달하는 서버여야 합니다. 지원되는 `local_coordination` 인자가 있으면 그대로 보존합니다. 통합 서버를 공개 연구용 서버로 교체하지 마세요.

키 하나만 바꾸는 이 절차를 쓰기 전에 최신 MCP `policy`와 비공개 설정을 읽어 기존 정책이 정확히 12/3600/600이고, 검토한 서버 패치 결과가 원본과 바이트 단위로 같은지 확인하세요. 다르면 중단합니다. 범용 도구는 명시적으로 요청한 다른 변경도 지원하므로, 아래 옵션만으로 이번 절차의 전제까지 강제되지는 않습니다.

정확한 해시를 확인한 뒤 root 인증으로 실행하는 명령 형태는 다음과 같습니다. 대문자는 실제 해시로 바꿔야 하는 자리표시자입니다.

```sh
python3 /root/reviewed/new_incident_policy_deployment.py \
  --source-dir /root/reviewed/source \
  --expected-core-sha256 INSTALLED_CORE_SHA256 \
  --expected-server-sha256 INSTALLED_INTEGRATED_SERVER_SHA256 \
  --candidate-core-sha256 INSTALLED_CORE_SHA256 \
  --new-incident-cooldown-seconds 600 \
  --max-claims-per-24h 24
```

이 명령은 별도로 승인된 운영 배포에서만 실행합니다. root 인증이 필요하고 broker 소켓과 서비스를 잠시 중지했다가 시작하며, 코드·설정의 비공개 백업을 남깁니다. 도구가 claim을 만들거나 콜백을 재전송하거나 시작 명령을 실행하지는 않습니다. 재시작 뒤 정상 감시 경로가 현재 조건에 따라 정책 제한 해제 이벤트를 전달할 수는 있지만, 그 이벤트도 실행하려면 새 claim이 필요합니다.

## 확인과 원복

도구의 반환 정책과 최신 읽기 전용 MCP 상태에서 `max_claims_per_24h=24`, `cooldown_seconds=3600`, `new_incident_cooldown_seconds=600`을 확인합니다. 짧은 간격을 적용할 새 장애가 없으면 실제 적용 간격이 3,600초로 나오는 것도 정상입니다. 기존 claim 집계는 유지합니다. 같은 집계 기간의 25번째 claim 거부는 격리 시험으로 확인하며, 운영 서버에 시험 claim을 만들지는 마세요. `retry_at`은 참고 시각이며 시간이 지났다는 이유만으로 실행할 수는 없습니다.

설정은 JSON으로 읽은 값끼리 비교하세요. 도구가 키 순서와 서식을 다시 작성합니다. 통합 코어·서버의 내용, 한도 키 이외의 비공개 설정, 구독과 실행 승인 이력이 보존됐는지 확인합니다. 로컬 복구 정책도 유지하세요. 이후 실제 복구를 확정하려면 외부의 새 SSH·ping 관측이 필요합니다.

12회로 되돌릴 때는 시작 정책이 24/3600/600인지 확인하고, 같은 소스 보존 절차에서 `--max-claims-per-24h 12`를 사용합니다. 원복에도 최신 정상 관측과 진행 중인 작업이 없어야 한다는 조건이 적용됩니다. 장애 중 긴급 중지가 필요하면 이 조건을 우회하지 말고 기존 [중지와 원복 절차](../../docs/experimental-recovery.ko.md#중지와-원복)를 따르세요. 이미 12회를 넘게 사용했다면 이전 claim이 충분히 집계 대상에서 빠질 때까지 새 실행이 제한될 수 있습니다. 낮아진 한도에 맞추려고 과거 DB를 복원하거나 기록을 지우지 마세요. 배포 중 새 claim이 생기면 운영자 확인을 요구하는 기존의 보수적인 원복 절차를 유지하며, 원장은 복원하지 않습니다.

이번 증설로 반복 단절의 원인, #79의 이벤트 수신 후 미실행 문제, #80의 나머지 진단·사전 경고·임시 추가 예산 과제가 해결되는 것은 아닙니다. 이 작업의 격리 시험이 운영 반영이나 무인 복구 성공을 입증하지는 않습니다.
