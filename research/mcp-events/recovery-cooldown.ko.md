# 정상 복구 후 새 장애의 실행 간격

[English](recovery-cooldown.md)

#61에서 다루는 선택적 정책이며 #44의 일부입니다. 이전 장애가 정상 복구된 뒤
새 장애가 발생했다면 이전 실행 때문에 무조건 한 시간을 기다리지 않도록 합니다.
같은 장애에서 결과가 불분명한 명령을 다시 실행하는 기능은 아닙니다.

## 설정과 적용 조건

기본값은 기존처럼 24시간 내 최대3회, 실행 간격3600초입니다. 이미 설정된 값도
유지합니다. 운영 시험에서는 기존12회/24시간과 전역3600초를 그대로 두고 다음
설정 하나만 추가합니다.

```json
{"recovery_new_incident_cooldown_seconds": 600}
```

설정을 생략하거나 `null`로 두면 기존 동작을 유지합니다. 켜려면300초 이상,
설정된 전역 간격 이하의 정수를 지정해야 합니다. 참·거짓 값, 문자열, 범위 밖
숫자는 거부합니다.600초는 **이전 claim 시점부터** 계산하며 새 장애나 복구
확인 시점부터 계산하지 않습니다.

다음 조건을 모두 충족한 새 대기 장애에만 짧은 간격을 적용합니다.

- 유일한 최신 claim의 장애와 다른 장애이며, 그 장애의 정상 복구 확인 이후에
  생성됐어야 합니다.
- 이전 claim의 장애가 종료됐고 최초로 인정된 명시적 결과 보고가 성공이어야 합니다.
- claim 이후 서로 다른 `verified_running` 관측이 연속3회 이상 있어야 합니다.
  SSH와 ping이 모두 정상이고 로컬 오류가 없어야 하며, 관측은 최소60초에 걸쳐
  쌓이고 각 간격은150초를 넘지 않아야 합니다.
- 증거는 `recovery_confirmations` 표에 해당 장애와 연결해 저장합니다. 기존의
  종료 기록이나 성공 보고 문장만으로 인정하지 않습니다. 원장이 모호하면 전역
  간격을 적용합니다.

인정된 오류·부분 정상 관측은 확인 중인 연속 횟수를 초기화합니다. 같은 관측의
재전송이나 거부된 오래된·역순·잘못된 요청으로 횟수를 늘리지 않으며, 거부된
요청은 증거를 수정하지 않습니다. 관측 공백이 길어져도 다시 시작합니다. 이미
확인된 정상 복구의 경계는 이후 장애와 서버 재시작에도 보존하지만, 새로운 claim이
다른 장애의 증거를 가져다 쓸 수는 없습니다.

증거를 저장할 자리는 새 코드가 claim을 발급할 때 함께 만듭니다. 기존 claim이나
구버전 코드로 발급한 claim은 새 정상 관측이 들어와도 단축 대상으로 소급 인정하지
않습니다. 최초 명시적 결과는 `recovery_reports`에 별도로 저장하므로, 불명으로
보고한 뒤 성공으로 정정해도 짧은 간격의 근거가 되지 않습니다. 기존 결과 보고
인터페이스가 불명 상태를 갱신할 수는 있지만 최초 보고의 근거는 바뀌지 않습니다.

이전 결과가 불명·실패·차단이거나 증거가 부족하면 기존 전역 간격을 적용합니다.
일일 한도는 항상 적용하며, 한도가 더 늦게 풀리면 그 시각이 `retry_at`이 됩니다.
같은 장애의 중복 claim, 만료된 승인, 오래된 관측, 권한 확인과 실행 결과 불명에
대한 제한도 유지합니다.

## 상태 확인

`policy.cooldown_seconds`는 기존 전역 간격이며 다음 항목이 추가됩니다.

| 항목 | 의미 |
|---|---|
| `new_incident_cooldown_seconds` | 선택적으로 설정한 간격입니다. `null`이면 꺼져 있습니다. |
| `effective_cooldown_seconds` | 조회한 장애에 실제 적용할 간격입니다. |
| `cooldown_basis` | `global` 또는 `confirmed_recovery`입니다. |

`incident.first_report`에서 처음 인정된 결과와 시각을 확인할 수 있습니다. 나중에
화면상의 결과가 정정됐다는 사실만으로 짧은 간격을 적용하지는 않습니다.

조건을 충족한 새 대기 장애가 없다면 설정값600초와 실제 적용값3600초/global이
함께 나오는 것이 정상입니다. 설정이 무시됐다는 뜻은 아닙니다. 실행하려면 여전히
최신 장애 상태를 확인하고 새 claim을 받아야 합니다. `retry_at`이나 후속 이벤트는
실행 권한이 아니며 ChatGPT가 즉시 처리한다는 보장도 아닙니다.

기존의 정책 제한 해제 이벤트를 재사용합니다. 제한 때문에 보류된 장애가 실행
가능해지면 정해진 한도 안에서 후속 이벤트를 보내지만, 이미 실행했거나 종료된
장애에 다시 실행할 권한을 주지는 않습니다.

## 운영 적용과 원복

dots-tailscale 일반 설치는 이 연구 서버를 배포하지 않습니다. 격리 검증을 거친
운영 배포 도구를 사용하고 전역 간격·일일 한도·claim/event 이력·구독·인증 정보를
보존하세요. KR의 기존 메일 커넥터 변경도 유지해야 합니다. 서버 파일 전체를
덮어쓰지 말고 `load_recovery`에 필요한 인자만 추가합니다.

`new_incident_policy_deployment.py`는 최신 외부 관측이 정상이고 복구 작업이
진행 중이지 않을 때, 지정된 소스와 설정만 적용합니다. 읽기 전용 사전 확인에서는
새 core를 실제 DB에 로드하지 않습니다. 생성자가 새 표를 만드는 작업은 통제된
배포 단계에서만 수행합니다. 코드와 설정을 비공개로 백업하고 실패하면 이 두
가지만 원복합니다. **claim이나 콜백 진행을 되돌리려고 DB를 복원하지 마세요.**
코드를 되돌려도 새로 추가한 증거 표는 남아 있어도 됩니다. 서비스 재개 후 새 claim이
발급됐다면, 구버전으로 자동 원복하지 않고 브로커를 중지해 운영자 확인을 요청합니다.
서로 다른 버전이 임의로 처리한 보고의 최초 시점을 소급 증명할 수는 없습니다.

운영 검증을 위해 시험 claim, 장애, 콜백이나 복구 명령을 만들 필요는 없습니다.
설정된 정책·서비스·최신 관측과 새로 발급한 claim의 정상 증거를 확인하세요. 기존
claim만 있다면 증거가 소급 생성되지 않는 것이 정상입니다. 이후
실제 장애 복구는 별도의 실측입니다. 짧은 간격을 끄려면 통제된 설정 변경으로 새
항목을 삭제하거나 `null`로 돌리고, 기존 예산과 이력은 유지하세요.
