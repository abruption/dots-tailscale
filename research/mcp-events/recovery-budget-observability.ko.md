# 복구 예산 진단과 운영자 알림

[English](recovery-budget-observability.md)

이 문서는 기존 인증된 `POST /monitor/observations` 응답에 담기는 읽기 전용
진단 정보를 설명합니다. claim 한도, 실행 간격, 자격 판정, 이벤트 전달 또는
실행 권한을 바꾸지 않습니다. 현재 운영 한도는 24회이며 새 설치의 기본값은
계속 3회입니다.

## 집계와 의미

요약은 복구 정책과 같은 엄격한 최근 86,400초 조건인 `claimed > now - 86,400`을
사용합니다. 발급된 claim은 보고 결과와 관계없이 모두 횟수에 포함됩니다.
결과 불명, 보고 누락, 실패, 차단, 성공은 claim을 돌려주지 않습니다.

- `claims_issued`와 `cap`은 요약 시각 `as_of` 기준 사용량을 보여줍니다.
- `budget_release_at`은 한도 소진 때만 표시합니다. 같은 한도 계산에서 필요한
  가장 오래된 claim이 집계 기간을 벗어나 사용량을 줄일 수 있는 가장 이른
  시각입니다. 예산만 고려한 재확인 참고 시각이며 `retry_at`이나 claim 허가가
  아닙니다. cooldown, 최신 관측, 장애 상태를 계속 확인해야 합니다.
- `first_reports`는 최초로 인정된 명시적 결과를 셉니다. `unknown`은 결과 불명
  보고가 있었음을 뜻하고, `missing`은 `recovery_reports` 행이 없다는 뜻입니다.
  오래된 기록일 수 있으므로 행이 없다고 보고 자체가 없었다고 단정할 수 없습니다.
- `current_outcomes`는 claim의 현재 수정 가능한 결과를 셉니다. 허용된
  unknown→success 정정 뒤에는 `first_reports`와 다를 수 있습니다.
- `externally_closed`는 SSH와 ping이 모두 정상이라는 새 관측 뒤 종료된 장애 수입니다.
  `sustained_confirmed`는 별도의 지속 확인 증거가 있는 claim 수입니다. 어느 값도
  시작 명령이 실제 실행됐다는 뜻은 아니며, 성공 보고 역시 독립된 실행 기록이 아닙니다.
- `unclaimed_followup`은 기존 복구 후속 안내 정책의 `operator_attention` 상태를
  전달합니다. 가용성, 운영자 주의 불리언, `awaiting_response`, 참고용
  `response_deadline_at`, 고정 사유 코드만 포함합니다. 기한은 claim 허가가 아니며
  응답 대기만으로 운영자 경고를 보내지 않습니다. 새 안내를 만들거나 Dots가 callback을
  읽었다고 추정하지 않습니다.

요약에는 장애·claim·이벤트 ID, callback URL, 인증정보, 보고 문장을 넣지 않습니다.
새 집계 SQL은 claim·보고 행을 Python 목록에 복사하는 대신 고정 크기 결과 한 건을 반환합니다. 기존 정책 상태 조회는 최근 claim 목록을 계속 사용합니다.

## 경고

비공개 notifier 설정에서 `operator_recovery_warnings`를 명시적으로 켜면 기본
경고 기준은 `ceil(한도 × 80%)`입니다. 한도가 24회일 때 20회부터 한도 근접,
24회부터 소진 경고를 표시하며 소진이 우선합니다. 기본 한도 3회에서는 근접 기준과
소진 기준이 같습니다. `recovery_budget_warning_percent`는 50~99 정수로 조정할 수
있고 생략하면 80입니다. `operator_recovery_warnings`가 true가 아니면 두 알림은 꺼져 있습니다.

한도 근접, 한도 소진, `operator_attention`은 각각 별도의 영속 dedup 상태를 사용합니다.
기존 승인된 notifier를 통해 알리기 전에 발송 시도를 저장하므로, 결과 불명인 전송을
즉시 재시도하지 않습니다. 기존 1시간 반복 제한은 각 종류에 따로 적용됩니다. 오래됐거나,
누락됐거나, 형식이 잘못됐거나 미래 시각인 요약은 **unknown**이며 0건이나 정상으로
판정하지 않고 기존 경고도 지우지 않습니다. 진단 필드가 없는 구형 health 파일은 계속
읽을 수 있지만, 새로 지원되는 응답을 받기 전까지 한도 경고를 보내지 않습니다.
한도 소진 알림에는 `budget_release_at`을 넣고, 그 시각이 지난 뒤에도 현재 실행 자격을
다시 확인하라고 안내합니다.

broker는 기존 인증된 machine-ingest 응답에만 선택적 요약을 넣습니다. relay는 고정된
스키마를 검증하고 원래 `as_of` 시각과 함께 기존 비공개 health 파일에 보관합니다. 구형
broker가 이 필드를 생략해도 처리되며, 선택적 요약 오류가 정상 관측 전달을 실패로 바꾸거나
relay가 재전송하게 만들지 않습니다. 현재 SSH 전송은 이 응답 요약을 돌려주지 않습니다. 이 기능에는 HTTPS를 사용하고 SSH 전송에서는 `operator_recovery_warnings`를 켜지 마세요. SSH와 함께 켜면 지원되지 않는 진단 경로로 판단해 감시 오류와 제한된 반복 알림을 냅니다.

일치하는 #79 소스 묶음 위에 검토된 `recovery_core.py`, `recovery_followups.py`, `monitor_ingest.py`, `recovery_budget_diagnostics.py`를 함께 반영해야 합니다. 코어와 보조 모듈의 읽기 시각 인터페이스 및 claim 시각 인덱스도 이 묶음에 포함됩니다.
Mac relay/notifier에는 검토된 `monitor_relay.py`, `health_notifier.py`와 같은 진단 모듈이
필요합니다. 기존 root 배포 도구는 새 모듈을 staging하지 않습니다. broker 쪽 파일을 먼저
배포하고 Mac relay/notifier 파일을 적용하세요. 구형 relay는 선택 ACK 필드를 무시합니다.
원복할 때는 Mac relay/notifier 파일을 먼저 되돌린 뒤 broker 파일을 원복합니다. 새 relay는
구형 broker가 요약 필드를 보내지 않아도 unknown으로 처리합니다.

새 HTTP 경로, MCP 도구, OAuth 범위를 추가하지 않습니다. broker는 응답에 필요한 claim·보고·확인
집계만 읽습니다. 원장 행을 노출하거나 원장을 변경·복사하지 않으며 claim 이력을 초기화하거나
한도를 바꾸지 않습니다. 경고는 기존 승인된 발송 경로를 사용하고 명시적으로 켜야 합니다. 기존
root 배포 도구는 추가 모듈을 모릅니다. 운영에 배포할 때는 검토한 모듈을 relay·notifier 코드와
함께 고정된 staging 묶음에 넣어야 합니다. 시험은 fixture와 stub 발송자를 사용하며 실제
claim·callback·알림을 실행하지 않습니다.

이번 범위는 임시 claim 추가 한도를 제공하거나 기존 claim을 돌려주지 않습니다. 반복 장애의
근본 원인도 진단하거나 해결하지 않습니다.

최근 집계와 예산 해제 시각 조회가 전체 이력을 훑지 않도록 claim 시각에 인덱스를 추가합니다. 인덱스가 claim 내용을 바꾸거나 삭제하지는 않습니다.

운영자 경고를 켠 상태에서 진단 데이터나 재알림 구성요소를 확인할 수 없으면 기존 감시 오류의 유예·반복 제한에 따라 알립니다. 사용량을 0으로 만들거나 이전 경고를 해제하지 않고, 데이터 확인 불가로 보고합니다. 기존 ACK 전달은 성공으로 유지하며 이 알림 때문에 복구 이벤트를 다시 보내지는 않습니다.

전송 실패로 새 ACK를 받지 못했다면, 이전에 검증한 요약을 원래 신선도 한도 안에서 사용할 수 있습니다. 새로 받은 정상 ACK에 진단이 없거나 잘못됐다면 unknown으로 바꾸며, 예전 요약을 새 현재 값처럼 복원하지 않습니다. 진단 시각은 최대 150초의 경과 시간과 기존 5초 시계 오차 범위를 허용합니다. claim 만료나 실행 검사는 바꾸지 않습니다. ISO 마이크로초 반올림으로 실제로는 뒤인 참고 시각이 `as_of`와 같게 표시될 수 있어도 실행 허가는 아닙니다.

알림 상태가 손상됐거나 미래 시각을 담고 있으면 운영자가 확인할 수 있게 보존하고 제한된 감시 오류 알림을 냅니다. 알림을 다시 보내려고 상태를 조용히 비우지 않습니다. 실제 발송 실패나 전송 결과 불명은 대기·반복 제한 상태보다 우선해 보고하며, 경로별 결과는 따로 저장합니다.

선택 기능을 켜기 전에 고정된 전체 staging 환경에서 `monitor_ingest`, `monitor_relay`, `health_notifier`가 모두 import되는지 확인하고, 새로 검증된 ACK를 점검하세요. 일부 파일만 복사한 진입점을 실행하지 마세요.

읽기 전용 스냅샷 자체를 열 수 없다면 관측 접수는 성공으로 응답하되 구독·진단 상태는 알 수 없는 값으로 생략합니다. 읽기·쓰기 연결로 대신 열거나 DB를 만들고 고치지는 않습니다. 구독 여부를 이미 확인한 뒤 선택적 집계만 실패했다면 확인된 구독 값은 유지합니다. 격리 검증은 DELETE와 WAL 모드를 모두 다루며, 실제 운영 모드는 배포할 때 따로 확인해야 합니다.

새 ACK에서 구독 여부를 확인할 수 없으면 relay health 파일의 `subscription_active`는 마지막으로 알던 값을 유지합니다. 그 값만으로 현재 구독이 정상이라고 판단하지 마세요. 진단의 가용성과 원래 `as_of`는 따로 확인하며, 경고 기능이 켜져 있으면 진단 확인 불가도 감시 오류로 알립니다.
