## 이번에 직접 확인한 내용

새 SSH 연결에서 엄격한 호스트 키 검증이 성공했고, 공개 호스트 키 지문도 기존에 독립 확인한 값과 같았습니다. 설치된 공개 실행 소스 네 파일과 manifest는 Git의 **v0.4.0** 내용과 모두 일치했습니다. 내부 Tailscale은 **1.102.4**, 소켓을 명시한 로컬 상태는 **Running**이었습니다. 개인키·인증 파일·Tailscale state 본문을 읽거나 해시하지 않았습니다.

현재 SSH 환경은 UID 1000, PID 1은 bwrap입니다. 이 환경에서는 소켓이 보이지만 PATH에는 `/workspace` 경로가 없습니다. 이 결과를 에이전트나 GUI 터미널에도 그대로 적용할 수는 없습니다. 현재 부팅은 이번 복구 뒤 관찰한 부팅과 같으며, 단절 전 부팅과는 다릅니다. 부팅이 달라졌다는 사실만으로 VM 교체와 같은 VM 재부팅을 구분하지 않습니다.

**10:33:52~10:34:12 KST**, 10초 간격으로 세 번 측정했습니다. shim은 RSS 19,424~19,432 KiB, 스레드 7개, FD 10개였습니다. tailscaled는 RSS 45,532 KiB, 스레드 14개, FD는 20→21→20개였습니다. 로그 크기는 shim 39바이트로 같았고 tailscaled는 67,282→67,425바이트, SSH는 17,956→18,200바이트였습니다. SSH 점검 자체도 로그를 늘릴 수 있습니다. **20초 측정으로 장기 안정성이나 누수 부재를 판단하지 않습니다.**

## 이번 복구의 의미

담당 세션의 외부 기록에서는 10월 22일 **22:22:22**에 마지막 정상 SSH·ping, **22:23:27**에 첫 실패를 확인했습니다. 그러나 감시 전달은 그보다 앞선 **21:24**부터 끊겼습니다. SSH 재인증 뒤 이벤트가 전달됐고, Dots는 권한 변경 금지 지시와 정상 시작 과정의 chmod가 충돌해 처음에는 실행을 중단했습니다. 지침 수정과 재개 요청 후 10월 23일 **09:33:49**에 claim을 얻어 한 번 실행했고, **09:34:25**에 외부 SSH·ping 정상으로 복구를 확인했습니다.

독립적인 Dots 실행 경로로 연결을 살린 사례는 확보했습니다. 다만 사람이 인증·지침·재개에 개입했으므로 무인 자동복구가 완성됐다고 볼 수는 없습니다. 이벤트 HTTP 200, Dots 실행 보고, 외부 연결 복구는 각각 따로 기록해야 합니다. 일부 파일의 보존도 `/workspace` 전체 보존을 의미하지 않습니다.

## 다섯 연구 주제의 남은 조건

| 주제 | 현재 근거 | 남은 확인 |
|---|---|---|
| 상태 보존 | 소스 무결성·공개 SSH 신원 연속성, 부팅 변화 | 전후 파일 존재·공개 소스 비교, VM 교체와 재부팅 구분 한계 유지 |
| 독립 시작 | 외부 연결이 없을 때 Dots 실행 후 복구 | 인증·재개·지침 수정 없이 자연 장애 한 번 복구, claim 전 중단 보고 |
| 실행 위치 차이 | 현재 SSH의 UID·PATH·socket 관찰 | 같은 부팅에서 에이전트·GUI·SSH를 같은 시점에 비교 |
| 장시간 연결·복구 | 새 연결 성공과 짧은 자원 기준값 | 사전에 정한 장기 관찰, 기존 연결 생존과 새 연결 성공 구분 |
| 프록시 호환성 | 현 배포 조합의 연결 성공 | CONNECT·TLS·Upgrade 단계별 실패 표와 격리 회귀 근거 |

다음 관찰은 **24시간**, 기존 60초 외부 감시와 5분 간격·15초 제한의 자원 측정을 제안합니다. 이번 작업에서 새 상시 수집기·예약 작업·장애 주입은 설치하지 않았습니다. 추가 관찰 결과는 총 10 MiB로 제한하고, 기준을 넘으면 추가 수집을 중단해 검토합니다. 실행 예산은 기존 외부 정책인 24시간 최대 3회·1시간 간격을 유지하며, 알 수 없는 실행 결과를 무작정 재시도하지 않습니다. 로컬 watchdog과 합산한 전역 예산은 아직 없습니다.

호스트 키 변경, 소스 불일치, 인증 상태·신원 소실, 불명확한 실행 환경·관측 시각은 중단 조건입니다. 자원 관찰의 검토 기준은 구성요소별 RSS 256 MiB·스레드 128·FD 512, runtime 로그 합계 50 MiB입니다. 이는 실험용 상한이며 제품 보장값이 아닙니다. 초과 시 추가 능동 점검을 멈추고 알리며, 자동 삭제·재설치·강제 재시작으로 결과를 맞추지 않습니다.

자연 장애가 없었다면 결과는 24시간 정상 관찰로만 남깁니다. #20은 다섯 주제별 재현 조건·결과·한계와 영어·한국어 안내가 갖춰질 때 완료할 수 있습니다. 실제로 하지 않은 시험은 미검증으로 유지하거나 후속 이슈로 명확히 분리해야 합니다.

## 제한된 수집기 사용

`collector.py`는 위 자원 관찰 계획을 구현합니다. 실제 배치·시작 시각과 24시간 결과는 별도로 기록해야 합니다. 설정은 예제의 호스트 자리표시자를 검증된 대상으로 바꿔 저장소 밖 소유자 전용 0600 파일로 저장하고, 데이터 디렉터리는 0700으로 준비합니다. 인증정보는 설정에 넣지 않습니다.

`python3 collector.py --config /절대경로/collector.json --once`로 한 번 실행하고, `--once` 없이 계속 관찰할 수 있습니다. 처음 저장한 24시간 종료 시각을 재실행해도 연장하지 않습니다. `--duration`은 새 실험을 더 짧게 잡는 옵션입니다. 상태 파일을 지워 관찰 기간을 몰래 늘리지 않습니다.

SSH는 엄격한 기존 호스트 키 검증, 원격 명령 15초·외부 대기 20초 제한을 사용합니다. 부팅 ID는 원격에서 SHA-256으로 바꿔 보내며, 공개 소스 해시·버전은 첫 성공과 부팅 변화 때만 수집합니다. 개인키·state 본문·환경변수·명령행·원시 status는 기록하지 않습니다. 오류에는 인증 URL이나 SSH stderr 대신 일반 오류 분류만 남깁니다.

파일 잠금과 원자적 상태 저장을 사용하고, 표본은 0600 JSONL 파일로 최대 10 MiB까지 기록합니다. 작은 상태·잠금 파일은 이 표본 용량과 별도입니다. 기한이나 자원 상한에 도달하면 수집기만 정상 종료합니다. 서비스 관리자는 이 정상 종료를 무조건 재시작하지 않도록 설정해야 합니다. 데이터 디렉터리를 새로 만드는 후속 관찰은 별도 실행으로 명시합니다. 오프라인 검증 명령과 상세 계약은 영어 기록에 있습니다.
