# v0.7.0 source-baseline migration trial — 2026-10-28

This operator-authorized deployment tested one normal migration of an existing
Dots installation using the original published v0.7.0 executable sources and
manifest from commit `37a65891b87a4a09d9df40075a0599485b65e762`.
The follow-up documentation change does not alter those sources or release assets.

## Starting state and preparation

- Installed source package: **0.6.0**, all four source hashes matched its manifest.
- Declared installer baseline: **1.102.4**; actual CLI, daemon binary and running
  backend: **1.104.4** from the separately authorized earlier runtime update.
- An independent cloud GUI terminal was opened and checked against the SSH
  session's UID/boot identity. Only the external recovery task was paused.
- The original four v0.7.0 source assets and manifest were transferred into a
  private staging directory outside the installation and verified together.
- Existing binary hashes, public node/SSH identity digests and private-key file
  inode/UID/mode metadata were recorded. Private-key contents were not read.

## Explicit target and operation

The CLI uses its own parent directory as the default target when `DOTS_TS_DIR`
is absent. A staged source checkout therefore needs the installed target
specified independently from `--bundle`. The deployed command used:

```bash
DOTS_TS_DIR=/workspace/.dots-tailscale \
  python3 /workspace/.dots-tailscale-stage/release-v0.7.0-37a6589/dots-ts \
  update migrate-baseline \
  --bundle /workspace/.dots-tailscale-stage/release-v0.7.0-37a6589 \
  --confirm-recovery-terminal --json
```

This supplied the target explicitly before execution; it did not patch the
published CLI, modify its manifest or relax ordinary `update apply` guards.
The missing target prefix in the original documentation was found during
preparation. The GitHub Release description was corrected and the source-doc
correction is tracked in #59.

## Results

- Transaction `2778bd2f7611498fbd1a3166ab3f4758` reported
  `operation=migrate_baseline`, `state=applied`, `phase=complete`.
- The completion journal timestamp was **2026-10-28T02:20:11Z**
  (**11:20:11 KST**). The source backup and transaction records were retained.
- Installed package **0.7.0**, with all four hashes matching the published
  manifest; actual Tailscale remained **1.104.4**.
- CLI and daemon binary hashes were unchanged. The public node/SSH identities,
  boot identity and private-key inode/UID/mode metadata matched the baseline.
- A new strict-host-key SSH connection and relay ping succeeded after migration.
  The cloud terminal independently displayed package0.7.0, source integrity
  match and Tailscale1.104.4. No exact outage duration was measured.
- The journal's `external_ssh=pending` was left unchanged. External verification
  was recorded separately, rather than modifying a local-readiness result.
- The recovery task was resumed, cloud control returned to Dots, and a later
  fresh observation ACK confirmed `subscription_active=true`,
  `failure_class=ok` and `stale_delivery=false`.

## Other deployment roles

The Mac relay's two code files already matched v0.7.0. Its dedicated retained
Python 3.13.17 runtime and fresh delivery/subscription were healthy, so no code
replacement or restart was needed.

The v0.6.0-to-v0.7.0 changes do not alter active KR broker modules. Existing
KR mail-connector customizations in `oauth_adapter.py` and `server.py` predate
this release and were preserved; the server is not claimed to be byte-identical
to the public broker tree. Recovery service/socket, Caddy and audit timer were
active with fresh summaries and observations. No KR configuration, DB, trust
policy or service restart was needed for this release integration.

## Limits

This is one successful source-only migration in the maintainer's existing
installation. It does not validate a fresh v0.7.0 installation, another account,
live failure injection, interrupted-transaction repair, VM replacement, runtime
state downgrade or all future versions. It also does not test a new live
1.102.4-to-1.104.4 runtime update; the actual runtime was already 1.104.4.

The historical pre-publication review remains in
[security-baseline-20261028.md](security-baseline-20261028.md). No CA bundle,
private key, authentication state or trust policy was regenerated by this trial.
