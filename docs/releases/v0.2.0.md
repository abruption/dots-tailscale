# v0.2.0 release preparation

The release preparation PR does not publish a tag or GitHub Release. The following summary is ready for the eventual release description after merge and final verification.

## Release summary

This release hardens service detection and the local TLS/WebSocket shim used to connect Tailscale through the Dots proxy environment.

- **Service detection:** match the intended executable and component arguments, so unrelated commands do not suppress startup ([#12](https://github.com/abruption/dots-tailscale/pull/12)).
- **Setup deadlines and cleanup:** bound network setup stages, cap HTTP headers at 64 KiB, and reclaim sockets and workers on failure. Preserve established long-lived connections and concurrent HTTP uploads ([#13](https://github.com/abruption/dots-tailscale/pull/13)).
- **WebSocket acceptance:** verify the actual request nonce's Accept hash, status and upgrade headers, subprotocol, and extensions before releasing protocol bytes ([#14](https://github.com/abruption/dots-tailscale/pull/14)).
- **Compatibility:** retain Python 3.8 hashing and process inspection, normalize Linux leading-slash paths, and recognize PyPy and the actual Python interpreter.
- **Guides:** updated bilingual instructions, English-first language links, the actual Dots terminal screenshot, SSH onboarding, and reviewed staging/update steps.

Tailscale remains pinned to **1.102.4**. Run the start command after environment replacement; automatic startup is not registered. Actual auth-key enrollment has not been tested. The offline tests cover these fixes; they do not prove a new live deployment, current proxy compatibility, or persistence across another VM replacement. The screenshot documents an existing installation's checks and CLI version.

Read the [English usage guide](https://github.com/abruption/dots-tailscale/blob/main/docs/usage.md) or [Korean usage guide](https://github.com/abruption/dots-tailscale/blob/main/docs/usage.ko.md). These links use `main` until the release tag exists.

## Verification before the release PR

The combined fix candidate passed all 88 offline tests on Linux with Python 3.11 and 3.13, plus Bash syntax and ShellCheck ([CI run](https://github.com/abruption/dots-tailscale/actions/runs/38567107967)). On macOS, 77 applicable core tests passed on actual Python 3.8.20; the full suite requires Linux-oriented SSH/tools/path fixtures. This is offline verification, not a new live deployment. Recheck the release PR commit in CI before tagging.

## Maintainer publication steps

Perform these steps only after the release PR is merged and its exact commit is reviewed. They are instructions, not actions performed by this preparation PR.

1. Record the full release commit SHA, confirm its checks passed, and ensure `VERSION` reads `0.2.0`. Create an annotated `v0.2.0` tag on that commit and push the tag when publication is authorized. If the tag already exists, verify it points to that commit rather than replacing it.
2. Package only the reviewed tag into an existing private artifact directory. Set `artifact_dir` to that directory's absolute path and run the commands in Bash with `set -euo pipefail`, so a failed archive operation stops packaging. Keep the same four assets as v0.1.0:

   ```bash
   git archive --format=zip --prefix=dots-tailscale-v0.2.0/ \
     --output="$artifact_dir/dots-tailscale-v0.2.0.zip" v0.2.0
   git archive --format=tar --prefix=dots-tailscale-v0.2.0/ v0.2.0 \
     | gzip -n > "$artifact_dir/dots-tailscale-v0.2.0.tar.gz"
   git show v0.2.0:tailscale-setup.sh > "$artifact_dir/tailscale-setup.sh"
   git show v0.2.0:shim.py > "$artifact_dir/shim.py"
   ```

3. Inspect both archive member lists and compare the extracted script bytes with the individual assets. Record SHA-256 hashes of all four files. Do not package working-directory state, private keys, installed node state, certificates, or logs.
4. Use the **Release summary** above as the GitHub Release body. Change its usage-guide URLs from `main` to `v0.2.0` now that the tag exists. Create a draft release for `v0.2.0` and attach all four assets. Review the draft, target commit, body, and download contents before publishing.
5. Verify the published tag, release links, and asset hashes. Update any guide that still presents v0.1.0 as the current release only when v0.2.0 is actually published.

Installed copies are not updated by publishing a release. Follow the usage guide's staged update and rollback procedure while preserving authentication state and SSH identity.
