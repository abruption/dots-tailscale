# v0.5.0 — Experimental recovery research

These notes describe v0.5.0. Publication and uploaded artifact verification are
recorded on the GitHub Release; deployment to an existing environment is separate. Work is tracked in [PR #46](https://github.com/abruption/dots-tailscale/pull/46)
and issues [#20](https://github.com/abruption/dots-tailscale/issues/20),
[#43](https://github.com/abruption/dots-tailscale/issues/43), and
[#45](https://github.com/abruption/dots-tailscale/issues/45).

## Scope

The release adds experimental recovery research and operating documentation:

- Authenticated HTTPS observations from an external monitor, with delivery and
  subscription health checks.
- MCP events that ask Dots to inspect its cloud computer and obtain a durable,
  single-use claim before running the fixed existing startup command.
- Explicit claim eligibility reasons, earliest policy retry times and bounded
  notifications when a recorded policy restriction clears. A retry time is not
  execution permission; a fresh observation and accepted claim are still required.
- Preflight reporting for execution-environment failures, separate from policy
  restrictions and command outcomes.
- A separately deployed broker with a dedicated service identity, restricted
  Unix socket, bounded network work, resource limits and documented ingress rules.
- Bounded lifecycle observations and dated evidence of recovery behavior.

The research code is in [research/mcp-events](../../research/mcp-events/README.md);
the [operator guide](../experimental-recovery.md), [continuous-trial notes](../../research/mcp-events/continuous-trial.md),
[transport guide](../../research/mcp-events/relay-transport.md), and
[security notes](../../research/mcp-events/security-hardening.md) describe the
separate operational setup. [Lifecycle research](../../research/lifecycle-20/README.md)
tracks which environment guarantees remain unproven.

The four installed executable sources match v0.4.0 byte for byte. The standard
installer and updater install the same source bundle with new package metadata.
They do not install the research broker, register a Dots automation, configure an
external monitor or start a watchdog. Automatic recovery requires separate,
explicit setup and remains experimental.

## Evidence available during preparation

- The combined research suite passed **168 offline tests on Linux Python 3.12**
  during the policy-update validation. This is a dated research result, not the
  result of final v0.5.0 commit CI or a replacement for installer-suite checks.
- With the local watchdog disabled, the external observer recorded the following
  connection-loss/recovery intervals (KST):

  | First failed observation | First healthy observation | Observed interval |
  |---|---|---|
  | October 24, 13:26:06 | October 24, 13:33:41 | 7m 35s |
  | October 25, 00:30:18 | October 25, 00:40:03 | 9m 45s |
  | October 25, 06:43:56 | October 25, 06:51:30 | 7m 34s |

  The boot ID changed each time. This establishes a boot change, not VM
  replacement. These intervals are observation bounds, not exact command
  execution durations or recovery-time guarantees. Dots reported one startup
  command and success per incident; external connectivity was independently
  checked. The restricted server claim ledger was not independently inspected
  for these three cases.
- The separately deployed broker was checked after a server reboot. That result
  concerns broker supervision and persistence; it does not establish recovery
  across a Dots VM replacement.
- The October 24, 03:10:47–09:46:40 interval was blocked by the previous
  three-claims-per-day policy and required manual resumption. It is excluded
  from unattended recovery evidence.
- Around October 25, 11:58, the relay stopped forwarding observations while its
  running process referenced a removed Homebrew Python installation. A fresh
  interpreter succeeded. A relay-only restart at 12:02:36 restored fresh
  acknowledgements, an active subscription and zero consecutive delivery failures.
  The exact child-process exception was unavailable, so the interpreter upgrade
  remains a supported explanation rather than a confirmed root cause.

## Package and artifact contract

Tailscale remains pinned to **1.102.4**. The installed bundle consists of
`tailscale-setup.sh`, `shim.py`, `dots-ts`, `dots_proxy.py` and the matching
`source-manifest.json`. The manifest version must be regenerated from the
reviewed source checkout after updating `VERSION`.

The planned release keeps the existing eight-asset contract: ZIP and tar.gz
archives of the exact reviewed commit, four individual executable sources,
`source-manifest.json`, and `SHA256SUMS`. Complete source archives include research
files; the five-file installation bundle does not install or execute them.
Checksums establish artifact consistency, not independent publisher identity.

Prepare archives only after the final source and documentation changes are
committed. Verify archive contents and individual asset hashes against that same
commit, and run the manifest check before publication. Keep runtime databases,
credentials, private audit records, wheels built for a particular deployment and
local virtual environments out of release artifacts.

## Release gates

- Review and merge the release scope; regenerate and review the manifest; run
  installer checks and research CI on the exact release candidate.
- Verify both archives and every individual asset against the intended commit
  before creating or publishing a tag and release.

- Reconcile the three Dots execution reports with the restricted claim ledger
  before claiming independently verified execution counts.
- Continue account-linking, refresh/renewal and monitor-runtime maintenance
  validation. Setup with another account has not been reproduced.
- Keep [#44](https://github.com/abruption/dots-tailscale/issues/44) coordination
  work and [#31](https://github.com/abruption/dots-tailscale/issues/31) automatic

recovery for existing users. Deployment of final package assets is a separate
operation. Research observations and future fixes should continue to be recorded
without implying an execution latency guarantee or platform persistence contract.
