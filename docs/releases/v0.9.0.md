# v0.9.0 release preparation and verification notes

v0.9.0 is being prepared. This document is not evidence of a published release,
a signing run or an operating deployment. This is a preparation-time snapshot. Check the
[release page](https://github.com/abruption/dots-tailscale/releases/tag/v0.9.0)
for published artifacts and independently verify them before installing.

## Changes since v0.8.0

- [Bounded unclaimed-event follow-ups](../../research/mcp-events/recovery-followups.md)
  (#79, #84): optional semantic reminders after a genuine successful callback
  receipt, without resetting transport deliveries or bypassing single-use claims.
  Fresh eligibility, subscription and preflight checks still govern dispatch.
  Exhaustion, expiry and missing receipt evidence expose operator-attention states.
- [Budget diagnostics and operator warnings](../../research/mcp-events/recovery-budget-observability.md)
  (#80, #85): ID-free rolling claim totals and outcome aggregates in the existing
  observation acknowledgement, with separate optional warning categories for
  near/exhausted budgets and follow-up attention. Claims are not proof of execution.
  Unavailable or stale diagnostics do not become healthy or grant permission.
- [Stable backend-version diagnostics](../baseline-diagnostics.md) (#82, #83):
  recognize official even-minor stable combined `-t<9hex>-g<9hex>` suffixes,
  preserve the observed raw version and compare its underlying stable version.
  Connection-health decisions and command exit codes are unchanged. Published
  v0.8.0 artifacts do not contain this correction.
- An explicit [operating claim-cap override](../../research/mcp-events/recovery-budget.md)
  (#80, #81), without changing the repository default of three claims per rolling
  24 hours or erasing prior grants. This does not implement temporary escalation.
- A full English/Korean/Japanese/Simplified Chinese documentation audit (#77, #78)
  and updated installation examples in all four languages.

The Tailscale baseline remains **1.104.4**. Of the four installed executable
sources, only `dots-ts` changed since v0.8.0; this preparation changes their package
metadata, not their executable bytes relative to the merged implementation.
Package updates do not update Tailscale binaries or deploy the research server.

## Defaults and rollout boundaries

Unclaimed-event follow-ups remain disabled unless explicitly configured. The
example policy is 600-second spacing, at most three semantic reminders and a
7200-second lifetime; it is not an execution schedule or delivery guarantee.
Existing received rows without the new receipt evidence are not replayed.
Operator warnings also remain disabled (`operator_recovery_warnings` absent or
false). Their default 80% threshold means near-limit at 20 of 24 grants and
exhaustion at 24 of 24. Publishing does not select 24 for an operating server,
change existing cooldowns or enable either feature.

Deploy the full compatible broker source graph, including `recovery_followups.py`,
`event_core.py`, `recovery_core.py`, `monitor_ingest.py`,
`recovery_budget_diagnostics.py` and the integrated-server constructor wiring.
Preserve private OAuth/mail integration rather than replacing it with the public
example server. The policy-only deployment helper is not a feature installer.
Deploy the broker before the matching Mac relay/notifier/shared diagnostics;
reverse that order for code rollback. Warning integration requires the HTTPS
observation acknowledgement; the SSH transport does not supply these diagnostics.

Preserve authorization data, claim history, subscriptions, policies and ledgers.
Do not restore an older DB to undo code. Disable reminders and quiesce callbacks
before rollback; in-flight callbacks cannot be recalled. Read the linked feature
guides for exact dependencies, freshness, record limits and configuration bounds.

Ordinary installation does not register an MCP connector, subscription, task,
watchdog or VM boot hook. Existing `start.sh` tasks retain their current path.
The [preview support gates](../recovery-support-readiness.md) remain open:
second-account reproduction, arbitrary VM replacement and unattended lifecycle
support are not established, and no immediate execution or recovery SLA is claimed.

## Candidate and publication gates

The [provenance workflow](../../.github/workflows/release-provenance.yml) requires
an exact stable tag, matching `VERSION` and the original source manifest. Its
read-only validation precedes signing. An Actions candidate is not a published
GitHub Release and does not deploy services.

The signed candidate must contain ten files: the four executable sources,
`source-manifest.json`, ZIP and tar.gz archives, `SHA256SUMS`,
`release-provenance.json` and `source-manifest.sigstore.json`. The original
manifest and both archives are attested; the manifest binds the executable bytes.
`SHA256SUMS` covers the other nine files. Checksums and the descriptor do not
independently authenticate the publisher.

Before publication, verify the exact tagged commit, workflow/ref, original
manifest, all source hashes and both archive contents using a trusted preinstalled
verifier and independently obtained roots. Publish those original candidate bytes
without rebuilding them. Minimize the interval between tag creation and verified
publication; clone/raw URLs can work before the Release is published. No v0.9.0 signing-run or live-deployment evidence is
claimed by this preparation PR. Follow the [provenance guide](../release-provenance.md),
including independent bootstrap for pre-v0.8.0 updaters and an available cloud
recovery terminal.

## Validation scope

The merged implementation includes isolated fake-clock, SQLite, callback,
read-snapshot, diagnostic freshness and notification-state tests. These tests do
not exercise real ChatGPT execution, real alert delivery or VM replacement.
Release-preparation checks cover metadata, original source hashes, documentation
links and offline release tooling; exact-tag signing and operating rollout require
separate subsequent verification. Earlier operating recoveries are historical
observations, not trials of these newly opt-in features.
