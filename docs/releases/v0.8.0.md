# v0.8.0 release and verification notes

These notes describe the v0.8.0 source snapshot. Confirm that the
[release page](https://github.com/abruption/dots-tailscale/releases/tag/v0.8.0)
actually has published artifacts before installing. A Git tag or Actions candidate
alone is not a published GitHub Release.

## Changes

- Authenticated provenance for the exact original manifest before package update
  execution, with independent verifier/root preparation and explicit legacy
  bootstrap boundaries.
- Baseline diagnostics, read-only local bundle inspection and bounded/scoped
  rate-limit diagnostics and backoff.
- Default-off automatic source updates and coordinated local/external recovery
  with durable control, transaction, attempt and unknown-result fences.
- Confirmed-new-incident cooldown policy and explicit strict external health
  independent of the supported `prior_boot` watchdog diagnostic.
- Bounded shim admission, pinned CI/static checks, reviewed main protection and a
  discoverable private security-reporting policy.

New installations retain Tailscale **1.104.4**. The package and the Tailscale
CLI/daemon pair have separate update paths. Existing node state and SSH identity
are operational data, not versioned release assets.

## Candidate production and publication

The reviewed [provenance workflow](../../.github/workflows/release-provenance.yml)
requires an exact stable tag, matching `VERSION` and a clean original manifest.
A read-only validation job precedes the separate privileged signing job. The
workflow uploads an Actions candidate; it does not publish a release or deploy
services.

The candidate contains ten files: four original executable sources,
`source-manifest.json`, ZIP and tar.gz archives, `SHA256SUMS`,
`release-provenance.json` and `source-manifest.sigstore.json`. The original
manifest and both archives are attested; the manifest binds the four executable
source files. `SHA256SUMS` covers the other nine candidate files.

Before publishing, independently verify the exact source/ref/workflow and artifact
bytes with a trusted preinstalled verifier and separately obtained roots. Check
all source hashes and archive contents, then publish the original candidate bytes
without rebuilding them. The descriptor and checksums do not authenticate their
own publisher. The full policy, residual trust assumptions and first-upgrade
procedure are in the [provenance guide](../release-provenance.md).

An installed pre-v0.8.0 updater does not retroactively enforce this policy. Its
first upgrade requires independent proof and source-byte verification before any
candidate helper runs. Do not try a new CLI flag on an old updater and infer that
verification occurred. Maintain access to an independent cloud recovery terminal.

## Experimental support and operating rollout

Ordinary installation does not enable automatic updates, a watchdog, an MCP
connector, a subscription, a scheduled task or a VM boot hook. Existing tasks
calling `start.sh` remain on their current path until explicitly integrated.
[#45](https://github.com/abruption/dots-tailscale/issues/45) retains the real
cross-account and lifecycle support gates; this release does not establish
instant delivery, arbitrary replacement-VM recovery or a service SLA.

The existing self-hosted broker may have integrated mail/OAuth customizations.
Preserve those and all policies/claims/subscriptions/ledgers when applying reviewed
recovery-core changes. For the explicit-health protocol, deploy the compatible
broker first and the Mac relay second; reverse that order for code rollback.
Do not restore old ledgers. Verify fresh accepted observations and actual effective
policy rather than treating exit zero or a configured 600s value as proof of
external recovery. See [cooldown rollout notes](../../research/mcp-events/recovery-cooldown.md).

Security reports use the route in [SECURITY.md](../../SECURITY.md). Repository
settings and the public reporting route were verified without submitting a fake
vulnerability report. Dated development and bug-fix evidence remains in the
[development report](../validation/v0.8.0-development-review.md) and
[external-health follow-up](../validation/cooldown-external-health.md); later
release evidence must identify its own exact source and signing run.
