# GitHub 요청이 제한될 때 업데이트 확인하기

[English](update-check-resilience.md)

이 문서는 v0.8.0의 동작을 설명합니다. 배포 파일은 릴리스 페이지에서 확인하세요. 패키지를 설치해도 자동 업데이트가 켜지거나 복구 작업이 등록되지는 않습니다.

패키지 확인은 태그를 지정해도 인증 없는 GitHub REST 요청을 사용합니다. 공용 출구 프록시를 쓰면 이 설치에서 요청한 횟수와 별개로 해당 출구 주소의 한도가 먼저 소진될 수 있습니다. `rate_limited`는 확인 실패이며, 설치된 버전이 최신이라는 증거가 아닙니다. `GH_TOKEN`이나 `GITHUB_TOKEN`을 설정해도 이 요청이 인증 요청으로 바뀌지는 않습니다.

## 설치를 바꾸지 않고 로컬 묶음 비교하기

신뢰하는 장비에서 고정된 릴리스의 원본 소스 네 개와 `source-manifest.json`을 준비하세요. 발행 여부와 출처는 별도로 검증한 다음, 승인된 경로로 소스 묶음만 전송합니다. 비교 명령은 다음과 같습니다.

```bash
/workspace/.dots-tailscale/dots-ts update check --bundle /workspace/reviewed-release --json
```

이 명령은 묶음의 명세와 실제로 읽은 소스의 해시를 확인하고, 선언된 버전을 설치된 패키지와 비교합니다. 묶음의 코드를 실행하거나 파일을 교체하거나 서비스를 재시작하지 않고, GitHub에 접속하지도 않습니다. 최신 발행 여부나 배포자 신원을 새로 확인하는 것은 아닙니다. `selection`과 `evidence`는 모두 `local_bundle`이며, `trust`에도 이 한계가 표시됩니다. 로컬 버전이 더 높다는 이유만으로 승인된 안정 릴리스라고 판단하면 안 됩니다. 적용할 때 필요한 출처 검증과 복구 조건을 이 결과로 대신하지 마세요.

`--bundle`과 `--tag`는 함께 쓸 수 없고, 로컬 묶음에는 프록시가 적용되지 않습니다. 패키지나 묶음의 무결성 오류는 그대로 오류로 남습니다. 이전 도구에는 이 비교 옵션이 없습니다. 이전의 `update apply --bundle`은 설치 작업이지 읽기 전용 확인 명령이 아닙니다.

## 재시도 시각과 로컬 대기

기본 할당량이 소진된 HTTP 403과 HTTP 429는 계속 `rate_limited`로 보고합니다. 도구는 범위가 제한된 숫자 `Retry-After` 초와 `X-RateLimit-Reset` 시각, 그리고 계산한 `retry_at`만 보존합니다. 원시 오류 본문, 임의의 헤더, 토큰, 프록시 주소는 출력하지 않습니다. 쓸 수 있는 재시도 헤더가 없으면 로컬 재시도 대기 시간은 1분입니다. 큰 헤더 값은 최대 24시간으로 제한하며, `retry_at`은 참고 시각이지 코드 실행 허가가 아닙니다.

같은 명시적 프록시를 사용하는 다음 패키지 확인·알림 갱신·패키지 적용은 대기 시간이 끝날 때까지 비공개 로컬 오류 캐시에서 해당 실패를 반환합니다. 이때 JSON의 `evidence`는 `github_live`가 아니라 `rate_limit_cache`입니다. 태그를 바꿔도 알려진 한도 대기를 우회할 수 없으며, 다른 명시적 프록시는 별도 범위로 취급합니다. 성공한 릴리스 메타데이터를 캐시해 실패나 새 확인 결과 대신 쓰지는 않습니다. 캐시에는 현재 프록시 범위 하나의 해시만 저장합니다. 이는 가능한 경우에 적용하는 로컬 요청 억제이며, 여러 장비의 할당량을 조정하거나 동시에 발생한 첫 요청의 경합까지 막는 기능은 아닙니다.

오류 캐시가 잘못됐거나 미래 시각을 담거나, 안전하지 않거나 읽기 전용·접근 불가이면 그 캐시를 릴리스의 긍정적인 근거로 쓰지 않습니다. 새 GitHub 요청에서 유효한 응답을 받았다면 그 결과를 `evidence: github_live`로 보여주되 `warning: backoff_storage_unavailable`도 따로 표시합니다. 캐시 실패가 GitHub 응답 실패와 같은 것은 아니며, 오래된 성공 결과를 재사용해도 된다는 뜻도 아닙니다. 실제 요청이 실패하면 확인 결과도 계속 실패입니다. 새 제한을 저장할 수 없을 때도 같은 경고가 나오므로 명령을 반복하면 요청이 다시 발생할 수 있습니다. JSON이 손상된 캐시는 일반 파일·소유자·권한·링크 검사를 통과한 경우에만 새 제한 정보로 바꿀 수 있습니다. 안전하지 않은 파일을 따라가거나 고치지는 않습니다. 계속 폴링하거나 권한을 느슨하게 하는 대신 설치의 비공개 디렉터리를 확인하세요.

프록시의 호스트·scheme 대소문자와 마지막 `/` 차이는 정규화해 같은 대기 시간으로 처리합니다. 이후 소스·출처 증거 파일을 받다가 발생한 제한도 같은 창에 저장합니다. 알림 갱신은 이미 획득한 메타데이터 잠금을 재사용하므로 같은 잠금을 다시 잡으려다 캐시를 무시하지 않습니다. 로컬 bundle 확인은 안정 버전 선언만 비교하며 개발 버전을 정식 업데이트 후보로 안내하지 않습니다.

기존의 다운로드 시간·크기 제한, 저장소·태그·URL 검증, 명세 검증, 독립 복구 터미널 확인과 트랜잭션 보호는 유지합니다. 태그를 고정했을 때 API를 생략하는 단축 경로는 채택하지 않았습니다. 이를 도입하려면 #67에서 다루는 출처 검증을 포함해 안정 릴리스의 발행 확인을 보존해야 합니다.
